# Notebook 工作流：在浏览器里写第一段策略

到目前为止，你已经看过不少 K 线、价差、订单类型。这一课我们换一个角色：从"看"变成"写"。打开编辑器，在浏览器里跑你的第一段策略代码。整个过程不需要装 Python，不需要装 pandas，也不需要等任何服务器。

## 为什么从笔记本开始？

一条策略从想法变成可信结果，中间通常要经过十几次甚至几十次的"改一下、跑一下、看一下"。这个循环越短，你能尝试的假设就越多。

完整的回测（带费用、滑点、资金曲线、夏普）是必须的，但每次都跑完整回测会很慢，而且常常掩盖一个简单的问题：**信号本身到底长什么样？**

笔记本工作流的目标是把这个循环压到几秒：

- 改两行公式 → 立刻看到信号在哪些点位翻转；
- 发现逻辑写反了 → 在浏览器里改完再点一次"运行"；
- 觉得思路对了 → 一键"提升到服务器"，跑完整回测。

<KeyPoint title="迭代节奏决定上限">在浏览器里调好信号、再去服务器里量化表现，是绝大多数职业量化研究员的默认节奏。</KeyPoint>

## 策略 = 一个函数

整个 Quant Academy 的策略契约非常窄：你写一个名为 `run` 的函数，接收收盘价数组，返回一个字典，字典里至少包含一个 `signal` 字段。

```python
def run(close: list[float]) -> dict:
    # close 是按时间顺序排列的收盘价
    # 返回的 signal 必须和 close 等长
    return {'signal': signals, 'note': '可选的调试信息'}
```

`signal` 的每个元素取值只有三种：

- $+1$ 表示这一根 K 线"持有多头"；
- $-1$ 表示"持有空头"；
- $0$ 表示"空仓观望"。

最小的例子是均线交叉。设短均线为 $\mathrm{SMA}_s$、长均线为 $\mathrm{SMA}_l$，最朴素的信号公式是：

$$
\text{signal}_t = \begin{cases} +1, & \mathrm{SMA}_s(t) > \mathrm{SMA}_l(t) \\ -1, & \mathrm{SMA}_s(t) < \mathrm{SMA}_l(t) \\ 0, & \text{其它} \end{cases}
$$

这条公式翻译成 Python，配上 numpy，正好就是编辑器里默认样例的核心几行。

## 在编辑器里

现在打开编辑器，跟着默认样例先跑一遍，再动手改。

<KeyPoint title="试试看">[打开编辑器](/zh/editor)</KeyPoint>

进入页面之后注意三个东西：

- **样例下拉**：自带三个起点——`sma_crossover`（均线交叉，趋势跟随）、`mean_reversion`（布林带均值回归）、`momentum`（动量）。先选一个跑通，再开始改。三个样例都是"能跑、但故意写得保守"的版本，你的工作不是照抄，而是用它们当骨架。
- **Run 按钮**：点一下，Pyodide 会在浏览器后台加载（第一次慢一点，之后秒开），跑完后下方会显示信号曲线和最近几笔翻转点。如果代码里有语法错误或抛了异常，错误信息会直接显示在编辑器下方，不需要去翻浏览器控制台。
- **Promote to server**：把你刚写的代码原样送到服务器，跑一次完整回测，回到工坊页面看 tearsheet。这一步是有成本的（占用服务器资源、计算时间），所以建议先在浏览器里把信号确认好再去提升。

建议第一次的"练手实验"：把 `sma_crossover` 里的窗口长度从 20/50 改成 10/30，观察信号变密了还是变稀了；再改成 50/200，看看翻转间隔是不是直接拉到几十根 K 线一次。这个过程能帮你在一分钟之内体会"参数 → 信号密度 → 交易频率"的传导关系。

## 浏览器 vs 服务器

为什么不直接在服务器跑？为什么不全部放浏览器？答案是两层各有不可替代的角色。

**浏览器（Pyodide）这一层**负责快速迭代：

- 零安装，秒级反馈；
- 没有真金白银的回测细节（费用、滑点、资金曲线），所以反馈快；
- 包是受限的：只有 `numpy`、`pandas`、`math` 这些；不能联网、不能读文件。

**服务器（qa_sandbox）这一层**负责量化结果：

- 跑完整 vectorbt 回测，给出夏普、最大回撤、交易明细；
- 在一个加固过的沙箱里执行你的代码，安全边界比浏览器更严；
- 速度慢一点，但出来的数字才能写进策略报告。

记住这个分工：**浏览器是草稿纸，服务器是评审席**。两层之间共享同一个 `run(close)` 契约——也就是说，在浏览器里跑通的代码，原封不动地送上服务器就能跑，不需要为了不同环境写两份逻辑。这一点很重要，因为它让你能放心地把绝大部分调试时间花在浏览器里。

## 常见错误

第一次写 `run` 函数时，最容易踩的两个坑都在"返回值"上。

<Pitfall title="忘了 signal 字段，或者长度对不上">
返回字典里**必须**有一个键叫 `signal`，否则后端直接报 `MissingSignal`。另外 `signal` 的长度必须**严格等于** `close` 的长度——少一个、多一个都会被拒收。如果你用了 SMA、EMA 这类滑动窗口指标，记得把前面 N-1 个还没成形的位置补 $0$，而不是 `NaN` 或者直接截断。
</Pitfall>

另外两个小细节也值得提前知道：

- `signal` 里的元素必须是 Python 的 `int`，不要直接塞 numpy 的 `int64`——浏览器侧的 JSON 序列化会出错。`int(x)` 一下就能解决。
- `run` 函数里不能有 `print` 之外的副作用：不能写文件、不能 import `requests`，浏览器和服务器都会拦下。
