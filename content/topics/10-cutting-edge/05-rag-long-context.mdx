A pretrained LLM is a frozen artifact of whatever it saw during training.
The world keeps moving. Your company's documents change daily. The user
asks about events from last week. Two strategies handle this:

- **RAG** (retrieval-augmented generation): bolt on an external index;
  retrieve relevant text per query; let the LLM read it.
- **Long context**: just stuff everything into the prompt and let the
  model find what it needs.

These are not opposites. They are points on a spectrum, with different
costs and failure modes. The right answer is usually both.

## Why this matters

Hallucination is the dominant correctness failure of LLMs. Most
hallucinations are confabulations from parametric memory — a fact-shaped
guess. RAG replaces that with retrieval-shaped grounding: the model
generates from text that is *currently in front of it*. Done well, it
turns "the model said so" into "the model summarized this source," which
is auditable and updatable.

## The standard RAG pipeline

A baseline RAG system is four stages.

### 1. Chunking and embedding

Split documents into chunks of a few hundred tokens (semantic, sliding,
hierarchical — many options, none perfect). Encode each chunk with a
dense embedding model into a vector $\mathbf{e}_d \in \mathbb{R}^{d}$.
Store in a vector database (FAISS, Qdrant, pgvector).

### 2. Retrieval

Encode the query: $\mathbf{e}_q$. Retrieve the top-$k$ chunks by inner
product or cosine similarity:

$$
\text{score}(q, d) = \frac{\mathbf{e}_q^\top \mathbf{e}_d}{\|\mathbf{e}_q\| \, \|\mathbf{e}_d\|}
$$

Bi-encoders are fast: a single forward over $q$ and a vector lookup
across millions of chunks.

### 3. Reranking (optional but standard)

Bi-encoder retrieval is approximate. A **cross-encoder** scores
$(q, d)$ jointly — concatenate them, run a model, get a score — and
reranks the top-100 down to the top-5. Slow but much more accurate.

### 4. Generation

Format the top-$k$ chunks into a prompt:

```
Use the following sources to answer.

[Source 1] ...
[Source 2] ...

Question: ...
```

The LLM produces an answer, ideally with citations.

```python
from sentence_transformers import SentenceTransformer, CrossEncoder
import numpy as np

embedder = SentenceTransformer("BAAI/bge-large-en-v1.5")
reranker = CrossEncoder("BAAI/bge-reranker-large")

docs = [...]  # your chunks
D = embedder.encode(docs, normalize_embeddings=True)

def search(q, k=20, top=5):
    qv = embedder.encode([q], normalize_embeddings=True)[0]
    scores = D @ qv
    idx = np.argpartition(-scores, k)[:k]
    rerank = reranker.predict([(q, docs[i]) for i in idx])
    order = np.argsort(-rerank)[:top]
    return [docs[idx[i]] for i in order]
```

## Long context: just put it all in?

Frontier models routinely accept 128k, 1M, even 10M tokens of context.
Why retrieve at all? In some workloads — read-this-codebase, summarize-
this-meeting — long context is genuinely cleaner.

But context is not free. Three problems:

- **Cost**: attention is quadratic at training, KV-cache linear at
  inference. 1M-token requests cost roughly 100× a 10k-token request.
- **Lost in the middle**: Liu et al. showed accuracy is U-shaped in
  position. A relevant passage in the middle of a long context is
  attended to *less reliably* than one at either end.
- **Distractors**: more text means more chances for the model to lock
  onto something irrelevant. RULER and NIAH-class benchmarks show
  graceful degradation at best.

<Callout variant="insight" title="The actual tradeoff">
RAG is precise but brittle (bad retrieval = bad answer). Long context
is forgiving but expensive and noisy. The right system uses RAG to
narrow the haystack, then long context within the narrowed scope. Pure
"throw 1M tokens at it" is rarely the optimum.
</Callout>

## What good RAG looks like in 2025

A handful of patterns matter more than the choice of vector store.

- **Hybrid retrieval**: combine dense (semantic) with BM25 (lexical).
  Acronyms, code, exact names — sparse retrieval still wins on these.
- **Query rewriting**: a small LLM rewrites the user query into one or
  more retrieval-friendly forms (HyDE: hypothetical document embeddings).
- **Multi-vector / late-interaction** (ColBERT-style): per-token
  embeddings give better recall at modest extra storage.
- **Reranking is usually a free win.** Always rerank.
- **Citations as a first-class output**: train or prompt the model to
  emit chunk IDs alongside claims; verify post-hoc.

## Failure modes to watch

- **Chunk boundaries split a fact in two.** Hierarchical chunking with
  parent-document return (chunk for retrieval, parent for context)
  helps.
- **The retrieved evidence is wrong.** The model will happily summarize
  bad sources. Quality of corpus is upstream of quality of generation.
- **Overconfidence on missing knowledge.** A well-instructed LLM should
  say "the sources do not address this." Prompt for that explicitly and
  evaluate it.

<Callout variant="warning" title="Eval before you ship">
RAG looks good in demos. The honest measure is recall on a held-out QA
set with ground-truth chunks, plus answer faithfulness on multi-hop
questions. Without these, you cannot tell if your retriever or your
generator is the bottleneck — and they need different fixes.
</Callout>

## Where this is going

- **Long-context models that genuinely retrieve well**: position-
  invariant attention, retrieval-as-a-built-in primitive.
- **Agentic RAG**: the model issues multiple search queries, refines
  them, decides when to stop. Already standard in deep-research products.
- **Memory + retrieval**: persistent per-user knowledge bases as a
  first-class part of the LLM stack, not a bolt-on.

The current consensus is sturdy: parametric memory for the long-tail of
common knowledge, retrieval for everything fresh, specific, or
auditable. Build for that division of labor.
