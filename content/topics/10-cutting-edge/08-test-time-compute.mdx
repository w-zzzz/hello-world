Throughout the GPT era, the dominant lever was *more parameters trained
on more tokens*. The 2024–2026 surprise is that you can buy comparable
gains by spending more compute *at inference time*. o1 and R1 (the
previous topic) are RL-trained for it. This module is about the
inference-side techniques — best-of-N, self-consistency, ToT, MCTS — that
work on *any* model, including ones never trained to reason.

These methods compose. A self-consistency wrapper around a CoT prompt is
two lines of code and a free quality boost. A full MCTS pipeline costs
much more but pushes small models into territory that used to require
frontier scale.

## The compute-quality curve

A central result of Snell et al. (2024) is that for a fixed total FLOPs
budget, splitting between *parameters* and *test-time compute* has a
non-trivial optimum. On hard reasoning tasks, a small model with generous
test-time compute often beats a much larger model with greedy decoding.

$$
\text{quality} \approx f(N,\ D,\ T_{\text{infer}})
$$

The reason: many reasoning errors come from sampling, not from the
underlying model knowing the wrong answer. Sampling diverse traces and
picking the best one converts *capability* the model already has into
*observed accuracy*.

## Self-consistency: the cheapest win

Self-consistency (Wang et al. 2022) is the canonical example. Given a
math problem:

1. Prompt the model with chain-of-thought instructions.
2. Sample $N$ independent traces with temperature > 0.
3. Extract the final answer from each.
4. Return the **majority answer**.

```python
from collections import Counter

def self_consistency(model, prompt, n=20, temperature=0.7):
    answers = []
    for _ in range(n):
        trace = model.generate(prompt, temperature=temperature)
        answer = extract_final_answer(trace)
        answers.append(answer)
    return Counter(answers).most_common(1)[0][0]
```

On GSM8K, this lifts CoT accuracy by 10+ percentage points with no
training and no architecture changes. The recipe is essentially free if
you have spare inference budget.

The catch: it only works when there's a discrete correct answer to vote
on. For free-form generation, you need something smarter.

## Best-of-N with a verifier

For tasks where the answer isn't a single number, replace the majority
vote with a **verifier** — either a learned reward model or a programmatic
checker (compiles? passes tests? matches schema?).

- Sample $N$ candidates.
- Score each with the verifier.
- Return the highest-scoring one.

This is the inference-time analog of RLHF. The verifier doesn't have to
be trained for this purpose specifically: a separately fine-tuned
process-reward model (PRM), or even the same LLM prompted as a judge,
both work. Best-of-N with a good PRM is one of the most effective
inference-time techniques on hard math.

## Tree of Thoughts: search instead of sampling

Linear CoT can't recover from a wrong early step — every later token
depends on it. Tree of Thoughts (Yao et al. 2023) treats reasoning as
explicit *search*:

- Each node is a partial reasoning state.
- The LLM expands a node by proposing $k$ candidate next steps.
- The LLM also *evaluates* each candidate (good/bad/promising).
- BFS or DFS through the tree, pruning low-value branches.

ToT shines on planning and puzzle tasks (Game of 24, crosswords) where
backtracking matters. The cost is large — many LLM calls per query — but
on tasks where greedy CoT scores 4% and ToT scores 74% (the original
paper's Game of 24 numbers), the trade is obvious.

## MCTS-on-LLMs and rStar

The natural extension of ToT is to use **Monte Carlo Tree Search** (the
algorithm that powered AlphaGo) to direct the exploration. The LLM
provides node priors (which child to expand) and value estimates (how
promising a partial trace is). UCT balances exploration and exploitation;
the tree grows until the search budget is spent.

**rStar-Math** (2025) takes this further into a *self-improvement* loop:

1. Run MCTS with the current policy and process-reward model on a math
   problem set.
2. Keep the high-quality traces MCTS surfaced.
3. Fine-tune the policy on those traces (SFT).
4. Retrain the PRM on the new data.
5. Repeat.

After several rounds, a 7B base model reached frontier-class performance
on AIME and MATH — a vivid demonstration that test-time search can
*generate the training signal* you need to improve the underlying model.
This blurs the once-clean line between "training" and "inference."

<Callout variant="insight" title="The compute-quality fungibility">
Test-time compute and parameter count are partially interchangeable. A
70B model with greedy decoding may match a 7B model with 64-sample
self-consistency at the same total FLOPs. Reasoning models (o1, R1)
collapse the trade by *training* the model to spend test-time compute
well. Pure inference-time scaffolding (self-consistency, BoN, ToT) gets
much of the same value with no training.
</Callout>

## Quiet-STaR: training models to think between tokens

Quiet-STaR (Zelikman et al. 2024) is a different point on the spectrum.
At training time, the model generates *internal* "thought" tokens before
each output token, and those thoughts are rewarded based on whether they
help predict the next text. The trained model "thinks" inline at
inference, no external scaffolding required. This is one of the
intellectual ancestors of o1-style reasoning training.

## The 2026 landscape, in one paragraph

If you have a reasoning-trained model (o3, R1), you usually want
*adaptive* test-time compute via the model's own thinking budget. If you
have a non-reasoning model and a verifier, **best-of-N with a PRM**
dominates. Without a verifier, **self-consistency** is the easy default.
For tasks with structured search spaces, **ToT or MCTS** is worth the
complexity. And if you can close the loop — generate traces with search,
distill into the model — you have **rStar-style self-improvement**, the
sharpest tool in this box.

<Callout variant="warning" title="Test-time compute is not free reasoning">
Sampling 64 traces costs 64x the inference. On a chat product serving
millions, this is the difference between a viable and non-viable
deployment. Pair test-time scaling with cheap routing: only escalate to
expensive inference when the easy path's confidence is low.
</Callout>
