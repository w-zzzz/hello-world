Attention's $O(n^2)$ time complexity gets all the textbook attention. The
practical cost, in 2024-era systems, is somewhere else entirely: it is the
$O(n^2)$ memory traffic between high-bandwidth memory and on-chip SRAM,
and the wasted compute on a serving cluster that wastes 80% of GPU
capacity on padding and idle batches.

FlashAttention rewrote the attention kernel. vLLM rewrote the way
inference servers handle memory. Together they are why every serious LLM
deployment in 2024 looks the way it does.

## Why this matters

A naive attention implementation produces a beautiful, correct, slow
program. Two changes — neither algorithmic, both *systems* — give roughly
$3{-}4\times$ training speedup and $20\times$ serving throughput on the
same hardware. Understanding them is non-negotiable for anyone shipping
LLMs.

## FlashAttention: IO-aware attention

The starting point is what the standard implementation actually does:

1. Compute $S = QK^\top \in \mathbb{R}^{n \times n}$, write to HBM.
2. Compute $P = \mathrm{softmax}(S)$, write to HBM.
3. Compute $O = PV$, write to HBM.

Each line touches an $n \times n$ tensor in global memory. For
$n = 8192$, the score matrix alone is 256 MB in fp16 — every layer, every
forward, every step. The arithmetic intensity is laughably low: lots of
memory bandwidth, very little FLOPs per byte.

FlashAttention's insight is that we never actually need the full score
matrix. Softmax is computable in **one pass** with running statistics:

$$
m^{(j)} = \max(m^{(j-1)}, \tilde m_j), \qquad \ell^{(j)} = e^{m^{(j-1)} - m^{(j)}} \ell^{(j-1)} + e^{\tilde m_j - m^{(j)}} \tilde \ell_j
$$

Combine that with **tiling**: load blocks of $Q$ and stream blocks of $K, V$
through SRAM. For each $(Q_i, K_j, V_j)$ tile, compute partial attention,
update the running $(m, \ell, O)$, drop $K_j, V_j$. The $n \times n$
matrix never exists. Memory traffic drops from $O(n^2 d)$ to $O(n d
\sqrt{M})$ where $M$ is SRAM size.

```python
# Pseudocode: outer loop over Q tiles, inner over K/V tiles.
for i in range(num_q_blocks):
    Qi = load(Q[i])
    Oi = zeros_like(Qi); mi = -inf; li = 0
    for j in range(num_kv_blocks):
        Kj, Vj = load(K[j]), load(V[j])
        Sij = Qi @ Kj.T / sqrt(d_k)
        m_new = max(mi, Sij.max(-1))
        Pij = exp(Sij - m_new)
        li = exp(mi - m_new) * li + Pij.sum(-1)
        Oi = exp(mi - m_new) * Oi + Pij @ Vj
        mi = m_new
    write(O[i], Oi / li)
```

This is *exact* attention — no approximation. Just a different schedule.

FlashAttention-2 reorders the loops to maximize work per warp.
**FlashAttention-3** (Hopper) exploits asynchronous TMA for memory and
WGMMA for matmul, overlapping copies with computation, and adds FP8
support — closing on 75% of H100 peak.

## vLLM: serving as a memory problem

Inference at scale is dominated by the KV cache. Every layer caches keys
and values for every token in every request. For Llama-3-70B at 4096
context, the cache is $\sim$1.6 GB **per request**. Pre-allocating that
contiguously, as early systems did, wastes most of it: requests finish
early, requests are short, and contiguous reservations leave holes you
cannot fill.

PagedAttention applies the OS textbook to this. Split the KV cache into
fixed-size **blocks** (e.g. 16 tokens). Each request has a small page
table mapping logical positions to physical blocks. Allocate blocks as
they fill; free them when the request finishes. Two consequences:

- **Near-zero fragmentation.** Memory utilization goes from ~20–40% in
  contiguous schemes to ~96% in vLLM.
- **Prefix sharing.** Two requests with the same system prompt point at
  the same physical blocks until they diverge. Production systems with
  long shared prefixes (e.g. "you are a helpful assistant…") get this for
  free.

<Callout variant="insight" title="The throughput unlock">
PagedAttention plus continuous batching — slotting newly-arriving
requests into a running batch instead of waiting for the slowest to
finish — turns a server that processes one request at a time into one
that processes hundreds simultaneously. The 24x throughput numbers in
the vLLM paper come from these two ideas together.
</Callout>

## Speculative decoding

Decoding is memory-bound: for each token, you re-read the entire model.
But the cost of running the model on a $k$-token sequence is roughly the
same as on one token. So:

1. A small **draft model** generates $k$ candidate tokens cheaply.
2. The target model runs *one* forward over the candidate sequence,
   producing logits at every position in parallel.
3. Accept the longest prefix where the target agrees with the draft;
   resample at the rejection point.

If the draft matches 70% of the time, you get a $\sim 3\times$ speedup
with mathematically identical output distribution. **Medusa**,
**EAGLE**, and self-speculation variants take this further by attaching
small auxiliary heads to the target model itself.

## What good serving looks like

A 2025 production stack typically combines:

- FlashAttention-2/3 in the model's attention kernel.
- vLLM (or TensorRT-LLM) with PagedAttention and continuous batching.
- INT8/FP8 weight + KV-cache quantization.
- Speculative decoding for chat workloads.
- Tensor parallelism within a node, replication across nodes.

Stack these and you can serve a 70B model at a few cents per million
tokens. Skip them and the same model costs ten times as much for the
same quality.

<Callout variant="warning" title="Profile, don't intuit">
"My LLM is slow" almost never means "FLOPs bound." It usually means the
KV cache is too big, batches are not being filled, the prompt prefix is
being recomputed, or you forgot to enable FlashAttention. Always profile
HBM bandwidth utilization before optimizing anything else.
</Callout>

## Continuous batching: the second half of the throughput story

PagedAttention solves the *space* problem; **continuous batching** (a.k.a.
in-flight batching, dynamic batching) solves the *time* problem. The naive
approach is "static batching": fill a batch of $B$ requests, run them
together, return when the slowest finishes. The wasted time is
catastrophic — short requests sit idle while long ones decode.

Continuous batching swaps requests in and out of the batch *every step*. A
request that finishes generates one final token, leaves the batch, and a
new request fills its slot on the next iteration. Combined with
PagedAttention (the page table makes mid-batch swaps cheap), this keeps the
GPU saturated. The vLLM and TensorRT-LLM throughput numbers (~24x over
naive servers) come from these two ideas working together.
