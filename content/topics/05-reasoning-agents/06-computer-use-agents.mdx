In late 2024 the frontier labs each shipped, within months of each other,
a new modality of agent: one that controls a real computer. Anthropic's
Computer Use (October 2024), OpenAI's Operator (January 2025), and Google
DeepMind's Project Mariner (December 2024) all answer the same question —
*what if the agent could just use the GUI like you do?* — with subtly
different bets about how.

This module is a tour of the design space. Pixel-grounded versus DOM-grounded.
Browser-only versus full desktop. What works, what breaks, why this is the
single most safety-relevant capability the field has shipped in a year.

## Why GUIs at all

The intuitive question is: why use a screen and a mouse at all? Most
information has an API; most actions can be scripted; agents already use
tool-call interfaces successfully.

Two answers:

1. **Long-tail integration.** APIs cover the head of the distribution.
   Internal corporate apps, legacy systems, half-broken government
   websites, every desktop application that does not expose an
   automation surface — these have *only* a GUI. A GUI agent solves them
   uniformly.
2. **Generalization.** A model that can see a screen and reason about it
   is a different kind of system than one that calls a fixed list of
   functions. It learns from the same distribution as humans (screenshots
   plus actions) and adapts to new interfaces without retraining.

The price is sample inefficiency, brittleness, and — most importantly —
a much larger attack surface. The agent now reads arbitrary text from
the web and treats it as instructions.

## Two grounding strategies

The defining technical question for a GUI agent is: how do you *ground* an
intended action in a concrete one?

**Pixel grounding** (Anthropic Computer Use, OpenAI Operator's CUA model).
The model sees a screenshot, decides "click the blue Submit button," and
emits an absolute pixel coordinate `(x, y)` plus an action verb (`click`,
`type`, `scroll`). Universal — any UI works — but vision is the bottleneck:
small targets, occluded targets, and scroll-dependent layouts are hard.

**DOM / accessibility grounding** (Project Mariner; many open-source frameworks).
The agent receives a parsed representation of the page (DOM tree,
accessibility labels, computed roles) and acts on element IDs. More reliable
when the structure is good; fails entirely on canvas-rendered apps, video,
PDF viewers, native desktop programs.

Production systems usually do both: render a screenshot *with element
boxes overlaid* (Set-of-Mark prompting), pass DOM as auxiliary text, let
the model reason in pixels and emit actions in selectors when possible.

## Anatomy of a step

A typical Computer Use loop looks like this:

```python
state = init_environment()  # VM with browser, apps
goal  = "Find the cheapest direct flight from SFO to JFK on 2026-06-01."
history = []
while not done(state):
    screenshot = grab_screen(state)
    obs = {"image": screenshot, "url": current_url(state)}
    plan, action = model.act(goal, obs, history)
    # action is e.g. {"type": "click", "x": 432, "y": 218}
    apply(action, state)
    history.append((obs, action))
```

Note what's *not* there: a fixed schema for the apps the agent uses, an
ontology of buttons, a list of allowed actions. The model just sees pixels
and decides.

## Benchmarks tell the story

Two benchmarks have become standard:

- **WebArena** (CMU, 2023): functional web tasks across realistic clones of
  shopping, GitLab, Reddit, Wikipedia. Tests web reasoning.
- **OSWorld** (HKU + Salesforce, 2024): full-desktop tasks on Ubuntu —
  open this PDF, edit it in LibreOffice, email it via Thunderbird. Tests
  multi-application workflows.

State of the art as of late 2025:

| System | WebArena | OSWorld |
|---|---|---|
| Claude 4 Computer Use | ~58% | ~45% |
| OpenAI CUA / Operator | ~55% | ~42% |
| Project Mariner (browser-only) | ~62% on web | n/a (browser-only) |
| Open-weights leader (UI-TARS-72B etc.) | ~50% | ~35% |
| Human baseline | ~88% | ~72% |

The gap to humans is the salient fact. We are not close to "general computer
operator" yet — but we are close enough that the safety conversations have
become urgent.

## The safety surface

Computer-use agents combine three things that, taken together, are
qualitatively new:

1. **Reading untrusted text** (web pages, emails) that may contain
   prompt-injection attacks crafted to redirect the agent.
2. **Writing untrusted output** (clicks, keystrokes) into systems that
   may have real consequences (sending money, sending emails, deleting
   files).
3. **Persistent state** that an agent can build up over many steps,
   sometimes hours.

Anthropic's standing recommendation — run only in an ephemeral VM with no
sensitive credentials, supervise execution, accept that some prompt
injections will succeed — is the conservative answer. The product
implications (Operator runs in the cloud in a sandboxed browser; Claude
Code asks for permission per shell command; Mariner currently restricts
itself to browser-only research-preview tasks) reflect the same caution.

<Callout variant="insight" title="Why this is not just RPA">
Robotic Process Automation has scripted GUI control for two decades. The
qualitative difference here is *generalization*: an RPA bot is brittle to
any layout change; a GUI agent reads the screen and adapts. This is what
makes the safety story new — you cannot whitelist the actions in advance,
because the action space is "anything a person could do at the keyboard."
</Callout>

- Run Anthropic's Computer Use reference VM. Watch a 5-minute task; you
  will learn more about the failure modes than any paper can teach you.

  safety-focused launches and worth studying as a template.
